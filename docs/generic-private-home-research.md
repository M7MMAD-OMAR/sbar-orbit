# Generic private application home, research only

Orbit's goal is an application beside the person: a separate display and pointer, familiar installed software and account context, and explicit shared working files. A filesystem layer can reduce profile copy cost. It cannot by itself make one live application profile safe for two independent processes.

This note records disposable fixture results from 28 September 2026. It adds no launch path and changes no user profile. The person's Zen profile, windows and pointer were not used.

## Current boundary

The generic native mount in `src/native/mount_unix.py:74-141` binds the host root and replaces `/tmp`, the user runtime directory and `/dev` with private mounts. Its optional `privateHome` branch replaces `/home` with a private home, currently used for Codex. Ordinary host files under `/home` remain reachable in the generic route. The narrow socket policy and the mount exceptions are described in `docs/personal-state.md`. The selected file lease in `src/native/file_leases.py:16-61` reserves exact regular paths, but the host editor does not participate in that lease. Zen has a separate minimal root and selected file mounts. VS Code, Zen and Codex already have different profile preparation paths in `src/native-vscode.ts`, `src/native-zen-launch.ts` and `src/native-codex.ts`.

These paths already show why one generic profile mount is insufficient: VS Code also uses a shared data database and Secret Service, Zen needs Firefox profile recovery and web isolation, and Codex's copied account record alone displays identity without loading projects or chats. The existing app pilots and their limits are in `docs/personal-state.md` and `docs/support-tiers.md`.

The FUSE test mounted and unmounted cleanly with `fusermount3`; all its fixture files were removed. Its source and upper behavior matches the [fuse-overlayfs layer model](https://github.com/containers/fuse-overlayfs/blob/main/README.md). These checks say nothing about a real account login or an installed application's nested sandbox.

## Candidate prototype

Use a sanitized, bounded profile snapshot as the lower layer, a session-owned upper layer for writes, and a minimal mount root. The lower must be generated by app-specific rules, not the person's entire home. A filesystem overlay is an optimization for starting and retaining a private copy, not a replacement for those rules.

1. In disposable fixtures, build an application manifest listing exact settings, state databases, credential dependencies and lock files. Reject symbolic links, hard links, special files and paths that change during capture. Use SQLite online backup for each database and record the source generation and backup time. Do not treat independently captured databases as one transaction.
2. Mount the vetted baseline read-only under `fuse-overlayfs`, with an Orbit-owned upper and work directory. Place the merged home behind the existing `privateHome` form of the bubblewrap mount, with a private runtime and bus. Keep the host `/home`, host display, input devices and broad session bus absent. Check the child's mount table, file descriptors, environment and socket reachability, including abstract sockets.
3. Grant working files separately by exact verified descriptor, using the existing lease for Orbit peers. Add a file broker before claiming reliable application save behavior: an inode mount can miss a host pathname replacement, and common editors save by writing a temporary file then renaming. The broker needs conflict detection against host changes and a recovery path before any write claim.
4. For one application at a time, supply only its required account material through an app-specific adapter or narrow credential service. Exercise a real authenticated operation, token refresh, restart, simultaneous host use and source hash checks. Keep an application at its measured tier until all these gates pass.
5. Destroy the FUSE mount and private processes together. If private state should persist, keep it in an Orbit-owned directory with a size limit and explicit lifecycle. Never merge arbitrary private profile writes back into the person's live profile.

## No-go limits

- Do not overlay the person's whole live home as a lower layer. It would expose unrelated files and profile internals and would not solve account or socket isolation.
- Do not mount the same writable browser or desktop profile into two running application processes. Singleton locks, SQLite journals, app caches and refresh tokens can conflict. A generic copy-on-write layer protects the source from writes but forks state after copy-up.
- Do not claim that a Btrfs snapshot, reflink or FUSE mount provides a consistent live account session. Keyring entries and D-Bus services live outside those file trees, and application authentication behavior must be measured separately.
- Do not claim shared file conflict safety from Orbit's lease alone. It coordinates Orbit launches, not the person's editor or a remote collaborator.
- Do not classify generic apps as private-home capable until the app's nested sandbox, helper processes, file portals, sockets and device needs pass the same negative controls. The current generic route still exposes ordinary host home files.

The next useful implementation step is a disposable prototype of the sanitized baseline plus private upper, followed by the negative controls above. A production adapter should be selected only after a real application's account and file operations pass while the person's own instance remains open.

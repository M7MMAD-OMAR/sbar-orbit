# Proton Pass private account pilot

Measured on 28 September 2026 with the installed Flatpak 1.40.2 ELF launched directly on Orbit's private Xwayland display. This is a diagnostic, not a supported account launcher.

The person's Proton Pass desktop process was absent during each copy. A Btrfs reflink copied the 252 regular files under the closed source `config/Proton Pass` tree to a new 0700 directory. The previous full profile audit counted 748 files including cache. The two test processes received a filtered D-Bus connection that could talk to `org.freedesktop.secrets`, plus separate `--user-data-dir` paths. The first used `--password-store=gnome-libsecret`; the second omitted that switch. Both ran under Orbit's resource limit and private display. The person's display and pointer were not used.

Both launches mapped one private window. A temporary private-frame OCR check detected Sign in text and no Unlock or vault label in either run. The frame was deleted immediately, and no vault item was opened or read. The original app was not launched to check whether its existing profile was still authenticated, so these results show only that the copies did not display inherited login in these conditions. Proton's [desktop source](https://github.com/ProtonMail/WebClients/blob/main/applications/pass-desktop/src/main.ts) uses a persistent Electron partition and flushes DOM storage at session end; the package's [changelog](https://github.com/ProtonMail/WebClients/blob/main/applications/pass-desktop/CHANGELOG.md) notes local session integrity checks. Neither source identifies the cause of these local sign-in screens.

The aggregate SHA-256 over the 252 source files stayed `2b89a8505e09136924fa51d33059072d09fffe980a8e04e8f57c4798f8bcf979` before and after both tests. The private app processes, profile copies and filtered bus proxies were closed and removed. The first process also raised `SIGTRAP` after mapping and left a truncated 2.6 MB root-owned coredump under `/var/lib/systemd/coredump`. The user account cannot remove that file without administrator privileges. Its contents were not inspected, so no claim is made about whether it contains process secrets. The earlier empty-profile pilot had also produced a root-owned core. The second test produced no new Proton coredump record in the checked journal window.

Account continuity, token refresh, vault access and operation alongside a running host Proton Pass remain not measured. Further private account pilots should wait for a launch route that prevents root-owned core retention and a known authenticated source state.

# Working beside the person with their applications

The acceptance target is an agent working on a private display with its own pointer and windows, using the person's installed applications, accounts, files and settings. When an application supports collaboration on a shared file or service, both people should see the same underlying work. The agent must not move or control the person's windows.

This is an application compatibility target, not a single switch. A private Wayland display cannot take ownership of a window that is already connected to the person's compositor. Sharing the person's D-Bus session can redirect a new application launch into the process on their desktop. Orbit therefore needs a separate application instance and a measured path to the same account or document for each application family.

## Acceptance for each application

1. Open the installed application version on Orbit's private display without opening or focusing a window on the person's desktop.
2. Match the person's relevant preferences and authenticated identity in a separate instance.
3. Read and write the intended shared file or service, then confirm the other instance sees the change in the way that application supports.
4. Restart the Orbit instance and confirm the expected account and work persist.
5. Verify that stopping Orbit does not terminate the person's application or alter its local profile unexpectedly.
6. Measure processor, memory and startup cost inside Orbit's shared resource budget.

Chrome, Claude Desktop, Codex, Nextcloud Desktop, Proton Pass and VS Code are initial application pilots. Their login stores, single instance behavior and packaging differ. VS Code has one measured GitHub identity result; a full coexistence result still needs a simultaneous host instance and service operation. Zen and Nextcloud showed account identity offline. Claude and Codex have private-window results without a verified authenticated service operation. Proton Pass has an empty-profile window result, but its copied account state remains unmeasured. No second Nextcloud sync client has been allowed to run against the user's sync folder.

The VS Code pilot used the application's [documented `--user-data-dir` and `--extensions-dir` flags](https://code.visualstudio.com/docs/configure/command-line) with `/usr/share/code/code`, not the launcher that detaches from Orbit's process group. The copied settings file was 3,892 bytes and its SHA-256 was `a4a551405dc8b438880c2dbfb345b04ecae325ad7e38e9533692a43b85a2524a` before and after the run. The private display's Extensions view listed Material Icon Theme as installed. The fresh application data still opened with a sign-in prompt. [VS Code's Settings Sync documentation](https://code.visualstudio.com/docs/configure/settings-sync) describes OS credential storage on Linux, so copying settings and extension files is not evidence of account continuity.

The later `launch-app` integration test returned `profileSnapshot: { settings: "copied", extensions: ["pkief.material-icon-theme-5.38.1"] }`, mapped one VS Code window on the private display, and wrote Arabic text to a shared disposable file through the copied `files.autoSave` preference. The Extensions view showed Material Icon Theme installed. The private runtime directory and application process disappeared after `session stop`. The source settings changed at 3:33 AM, before this test began at 3:35 AM. A controlled second launch began and ended with the same source SHA-256, `98c493ecd5c0c908ccb8c0dea8a66cb2c34487c7d102457eab9990a0410a986b`. This is evidence that the controlled run did not write the source file; it does not attribute the earlier change.

The account test exposed another VS Code path outside `--user-data-dir`: `~/.vscode-shared/sharedStorage/state.vscdb`. A full profile pilot without `--shared-data-dir` used that host database and changed its modification time. The corrected `launch-app` passes a private `--shared-data-dir`; its log named the private database, and the host database's modification time stayed at 4:00:50 AM through the corrected run. The account database `Code/User/globalStorage/state.vscdb` is copied with SQLite's online backup API, including uncheckpointed WAL data. The private VS Code process reaches only `org.freedesktop.secrets` through `xdg-dbus-proxy`, after a metadata check finds the `Code` key unlocked. The account menu in the private window showed the person's GitHub identity. After `session stop`, the proxy process and runtime directory were gone. This proves the GitHub identity in this VS Code build and host state; it does not prove Copilot API access, other sign-ins, or future token refresh.

The filtered proxy limits D-Bus service names, not keyring items. VS Code can enumerate the host keyring collection through that service while its private session runs. A synthetic one-item service worked for a simple libsecret lookup but VS Code crashed before reading a secret from it, so that narrower path is not claimed. The preflight refuses a missing or locked `Code` item before launch; a relock after launch remains unmeasured.

Codex Desktop's private-window pilot used an empty `CODEX_HOME` and a separate Electron user data path. Its window mapped and displayed Sign in, and the host application process and tracked host auth and Electron profile files stayed unchanged. A second pilot pointed the private Electron window at the host `CODEX_HOME`. The private window was still loading when a monitor found that `~/.codex/config.toml` had been replaced and shrunk from 6,136 to 6,094 bytes during startup. The pilot stopped immediately. Its baseline recorded a digest and metadata but not the original bytes, so the exact change and writer cannot be established. The host app remained alive and `auth.json` stayed byte-identical. This is evidence against treating a shared live `CODEX_HOME` as a verified path; no account UI was observed in that pilot.

Claude Desktop's private pilot copied a small subset of the live profile and offered the private app its `application=Claude` keyring item. The private UI showed the account and projects but requested sign-in again. The host log reported `basic_text` storage and said OAuth tokens would not persist; it later reported using an OAuth v2 token from memory. This makes a filesystem-only account copy insufficient in the measured host state. The installed launcher supports `CLAUDE_PASSWORD_STORE=gnome-libsecret`, but changing the host storage backend and its effects on old encrypted cookies have not been tested. No host launcher, app or profile was changed in that pilot.

A synthetic one-item Secret Service caused a later empty Claude pilot to crash inside `libsecret` before safeStorage reported its backend. A fresh empty Claude pilot with the real filtered Secret Service and `--password-store=gnome-libsecret` exited before mapping or writing its log, so that switch is still not validated for this packaged app. A disposable process reported `dumpable=0` after exec and a zero core limit; an intentional crash produced no core. The later Claude pilot also produced no core. The earlier crash left one root-owned core file under `/var/lib/systemd/coredump`; the user account cannot remove it without administrator privileges. No host Claude setting or process was changed.

The installed Proton Pass ELF mapped a private Xwayland window with a fresh empty profile and displayed Sign in with Proton, while the user's closed Flatpak profile stayed untouched. A Btrfs copy of that profile matched all 748 source files by hash. An account-copy pilot using a filtered Secret Service was stopped before account UI inspection when a child exited with `SIGTRAP`. Its core record stored no core file, and the source files still matched by hash and metadata. The earlier empty-profile pilot had left a 7.5 MB root-owned core file; it contained no copied account profile, but this user cannot remove it without administrator privileges. Proton vault contents were never opened or read in these pilots.

A disposable GTK probe inside Orbit's private display found OS permissions on render, sound and video nodes and connected to the host audio sockets without sending protocol data. Orbit then linked the two existing host audio sockets into its 0700 private runtime directory, without linking any display or input socket. A second private GTK application ran `pactl info` and `pw-cli info 0`; both commands succeeded and returned data while its runtime path and Pulse alias were private. The session stopped and its runtime directory was removed. The compositor reported `pixman` bound. Neither probe rendered with GPU, played or recorded audio, or read a camera frame. This establishes audio service access and device reachability, not functional driver parity.

Nextcloud Desktop has an active host sync client, so starting a second client with the original folder definitions could make both write the same sync database and files. A private pilot copied its config but removed all seven folder sync keys, used the supported `--confdir`, hid the host sync directory, config, lock and bus inside a bubblewrap namespace, and had no network route. The installed client mapped an Orbit window and showed the existing account identity with Offline status. Its private process held its own lock and no host sync or config file descriptors. The host client PID remained active, and inode, size, modification and change times of its config, sync database, WAL, SHM and lock matched before, during and after. The private session and config were deleted. Authenticated server access and simultaneous sync are not claimed.

Zen is running as a Flatpak with a live profile lock and SQLite WAL files. Opening that same profile in a second process risks its data; a private clone represents a point-in-time copy, not live synchronization of tabs. Ordinary `flatpak run` moves the app into `app.slice`, outside Orbit's resource budget. The deployed Flatpak contains an ELF that launched directly under Orbit's private display and `sbarorbit.slice`, first with an empty profile and then with a Btrfs reflink copy of the active profile. The copy was held in a 0700 directory. All 1,648 copied SQLite databases passed `quick_check`, its Mozilla recovery JSON contained 22 tabs, and its bookmarks table had 916 entries. The private window showed populated bookmarks and an account identity; the empty-profile control showed Welcome and Sign In. The private copy used a separate network namespace with no site traffic. No inspected private file descriptor pointed into the source profile, and the host Zen process stayed open through the private launches. The active source restarted independently between the initial baseline and the clone launch, so source modification times cannot attribute writes. The clone and all its private processes were removed. Cross-file atomic consistency and online authentication remain unproved; opening an authenticated copy online also needs an enforced network boundary.

A later empty-profile Zen pilot opened `https://example.com` on Orbit's private display through an HTTP CONNECT proxy. Direct TCP and DNS from its network namespace failed, the proxy admitted `example.com:443` and refused another authority, and the window title showed the public page. Sixteen browser descendants stayed in `sbarorbit.slice`; none held a file descriptor into the host Zen profile. All pilot processes and files were removed. This measured one allowed page and refused startup authorities, with no personal cookies. That pilot's root filesystem bind made some host Unix sockets potentially visible. A separate local `bwrap` probe demonstrated that a host Unix socket can be reached through such a bind even with `--unshare-net` and a read-only root bind. The tracked offline Zen launcher now uses a minimal mount root, and the shared proxy has since gained private-DNS rejection. Neither correction has been measured in an online Zen account copy. The proxy still validates CONNECT authority rather than the encrypted site's origin, so the personal clone remains offline.

The tracked Zen snapshot helper was also run against the current profile without opening Zen. It copied 13,249 regular files, 1,058,396,462 logical bytes and 1,644 SQLite databases into a disposable 0700 directory in 3.8 seconds. Three recovery files decoded, with 22 tabs in the first one. The source directory inode and modification time matched before and after; the disposable copy was deleted. A later `launch-app zen` run used the same active profile as an offline private copy. It mapped one window with restored sidebar tabs and bookmark icons in `sbarorbit.slice`; 16 private processes had no file descriptors into the source profile, and tracked source file metadata stayed stable. No host Zen process was running before, during or after that run. The clone was removed. A subsequent disposable-profile launch measured cleanup of the display directory after a cleanup race fix. The internal sandbox home path changed after those native runs, and that final path has unit coverage but no native launch measurement. Cross-file consistency, visible account identity in the tracked launch and online authentication remain unmeasured.

The active Zen profile is an ordinary directory inside the root-owned `/home` Btrfs subvolume, not a subvolume of its own. [Btrfs snapshots require a subvolume source](https://btrfs.readthedocs.io/en/stable/btrfs-subvolume.html), so this profile cannot be snapshotted alone atomically. A snapshot of all `/home` would include unrelated data and would need permissions and cleanup behavior not established for this user. The current per-file reflink copy with SQLite and recovery validation remains a usable-copy check, not a simultaneous snapshot of every profile file. Moving Zen's profile to its own subvolume would require a separate migration while Zen is closed and has not been attempted.

The Chromium origin lease now uses a minimal mount root rather than exposing the host root. The browser cannot reach the tested host socket under `/tmp`, and the host owns its CDP socket so a browser-controlled symlink cannot redirect the host's connection. Its private one-item D-Bus has an empty activation directory; a fixture could not start a host service while libsecret still read a synthetic item. The proxy now resolves a leased name once, connects to that checked numeric address, rejects private DNS answers for public names, and checks that a plain HTTP Host matches its leased URL. These changes are measured for the Chromium path. Zen uses a different control protocol and has not been connected to this lease. The system application mounts still need a socket inventory. CONNECT still checks authority rather than HTTPS origin or TLS SNI. A Zen account clone stays offline until a Zen-specific online path is implemented and measured.

A separate `public-web` proxy lease now exists for a future native browser route. It resolves names once, rejects local and private destinations, and connects to the checked public IP. A fixture sent a POST and then a GET for different hosts over one client connection without sending the second request to the first host. The lease owns and removes only its generated directory and terminates an open CONNECT tunnel on close. It has not yet been attached to Zen. CONNECT allows any valid port at a public address and cannot verify HTTPS origin inside the tunnel.

Generic Fedora application launch and VS Code `launch-app` now apply a Landlock pathname UNIX socket policy to the application process before exec. This machine's kernel reports ABI 10. The policy allows only captured socket inodes for Orbit's private Wayland display, private bus, optional filtered keyring proxy, intended host audio services and the exact private Xwayland socket when requested. A disposable fixture connected to its allowed socket while a second socket returned `EACCES`; an abstract socket outside the policy returned `EPERM`. The same child read and wrote an ordinary file and saved it by renaming within and across directories. Private Wayland, X11 and disposable VS Code launches mapped after the change, and a disposable Zen launch still worked through its separate minimal mount root. This applies to those application descendants, not to an unrestricted agent shell outside Orbit. An inherited connection, a socket created inside the same Landlock domain, network traffic and other ordinary file access are outside this particular policy. A repeat of the fifteen-application coverage run found the functional exceptions described in `docs/validation.md`; it does not establish support for every installed application.

The implementation path is a private display and private application process, selective snapshots of settings and local state, a restricted private application bus, and application specific credential access. The display, dconf snapshot, restricted bus and VS Code GitHub identity route now exist; other app state and credential paths remain open. Files remain the person's real files under their normal user permissions. A whole home directory copy is unsuitable here: the current config directory is 31 GB and the data directory is 146 GB. Copying them also risks duplicating live databases and lock files.
